# Сквозной аудит панели PrintFlow 9.2 — улучшения без потери безопасности

Дата: 25.08.2026. Это продуктовый и инженерный аудит всей панели: `site/index.html`, всех подключённых браузерных модулей, вспомогательных страниц, генераторов, Python-коннектора и точек запуска. Он дополняет `docs/АУДИТ-РЕПОЗИТОРИЯ.md` (надёжность) и `docs/ОПЕРАТОРСКИЙ-АУДИТ.md` (смена), а не отменяет их решения.

## Как читался код и что уже проверено

- Каркас: все 18 `view-*` в `site/index.html`, навигация, модалки, командная палитра и offline/API-состояния.
- Браузер: `qr.js`, `core.js`, `printer.js`, `ops.js`, `money.js`, `finance.js`, `shelf.js`, `products.js`, `bridge.js`, `marketing.js`, `workshop.js`, `app.js`; стили `theme.css`, `app.css`, `more.css`.
- Вспомогательные страницы: заказ, витрина, трекинг, калькулятор/ярлыки, дизайн, TV, катушка и все материалы в `site/materials/`.
- Коннектор: запуск (`pf.py`, `launcher_window.py`, `printflow_connector.py`), маршрутизация (`api.py`, `v9_api.py`), хранение (`db.py`, `repo.py`, `schema_v3.py`), производство, Bambu/FTPS/камера, финансы, склад, документы, CRM, аналитика, контент, обновление и Telegram. Полный перечень доменов приведён ниже.
- Статическая и регрессионная проверка после последних изменений: `python scripts/check.py` — 680 тестов, компиляция Python, проверка подключённых JS и HTML-контрактов. Это **не** заменяет тест реального P1S/AMS и браузерное E2E.

Главный вывод: функциональность уже очень широкая. Следующий прирост пользы даёт не ещё одна сущность, а уменьшение числа решений, которые оператор вынужден принимать в разных вкладках, и явное отделение «факта», «прогноза» и «черновика».

## 2. Сквозные проблемы интерфейса

1. **Не смешивать уровни достоверности.** У каждого числа и статуса нужен единый ярлык: факт / план / прогноз / черновик / требует проверки. Это важнее нового графика.
2. **Показывать объяснение запрета.** У недоступного запуска, выдачи, списания или оплаты должно быть одно действие «что исправить», а не только disabled-кнопка.
3. **Один безопасный путь для смены.** Обзор → принтер → очередь → приёмка → выдача. Ссылки между экранами должны сохранять контекст объекта, а не просто открывать вкладку.
4. **Мобильный режим — для действий, не для всех таблиц.** На телефоне приоритет: тревога, пауза/продолжение, фотография/статус, приёмка. Полный учёт и массовые таблицы — desktop-first.
5. **Единый журнал решений.** Наряду с техническими событиями хранить «кто подтвердил приёмку/брак/оплату, с каким комментарием». Не логировать секреты.

## 4. Вспомогательные страницы и генераторы

- `order.html`, `shelf.html`, `track.html`, `m.html`, `my.html`: каждый должен честно работать без панели или явно говорить, что часть данных требует локального коннектора. Нельзя подставлять демо-данные так, чтобы они выглядели как заказ клиента.

## 6. План внедрения: что делать первым

### P0 — уменьшаем ошибки человека (1–3 дня на небольшие части)

1. Единые ярлыки факт / план / прогноз / черновик во всех ключевых карточках.
2. Экран «следующие 3 действия» на обзоре, построенный только из уже существующих API-сигналов.
3. Объяснения блокировок preflight, выдачи, оплаты и запуска.
4. Замена наиболее рискованных `window.prompt` на модалки с валидацией и отменой.
5. Предпечатный чек QR/срока/цены в генераторах.

**Метрика:** оператор проходит «файл → печать → приёмка → выдача» без поиска по вкладкам и без необъяснимой disabled-кнопки.

### P1 — ясность и скорость (несколько заходов)

1. Разделение тяжёлых фронтенд-модулей без изменения API и DOM-контрактов.
2. Снимок расчёта в заказе и симулятор перестановки очереди без записи.
3. Статус свежести полочного ценника и контроль перепечатки.
4. В настройках — область действия, перезапуск и backup до рискованной операции.
5. Снимок «as of» для финансов и аналитики.

**Метрика:** меньше ручных сверок между вкладками; любое число имеет происхождение и дату.

### P2 — надёжность развития (крупнее, сначала план в роадмапе)

1. Декомпозиция `api.py`, затем `manager.py`/`accounting.py` по доменам.
2. Контрактные тесты статусов задания и миграций.
3. Реальный browser E2E: создать заказ → preflight → задание → факт → выдача/оплата, без запуска физического принтера.
4. Потоковая multipart-загрузка вместо разбора большого тела в памяти.
5. Hardware-in-the-loop стенд P1S + AMS для MQTT/FTPS/сбоя сети.

**Метрика:** изменения в одном домене не требуют ручной проверки всей панели; критический путь покрыт браузерным и серверным сценарием.

## 7. Не делать без отдельного решения владельца

- Не включать автозапуск печати, автопостинг или автоматическую рассылку клиентам ради «оптимизации».
- Не публиковать локальную панель, камеру, MQTT или FTPS в интернет; удалённый доступ — только через VPN.
- Не смешивать «магазин/дом/AMS» с отдельными учётными складами.
- Не выдавать прогноз цены, срока, прочности, налогов или безопасности за подтверждённый факт.
- Не заводить новую модель данных ради красивого виджета, пока не определён источник правды и миграция.
