## 2. Живой смоук (реальный HTTP, изолированная база, 127.0.0.1)

Сервер: `api.serve()`, отдельный `DATA_DIR`. Вызовы через `urllib`, гонки — 10 потоков.

| # | Сценарий | Результат |

| 6 | Тот же доход 1500,00 вторым контуром (`bank_import.apply_rows`) | в журнале **3000 вместо 1500** — двойной счёт ✗ |

## 3. Карта денег (как связано сейчас)

```
site/cashier.html (PWA, LAN)          site/sbp.html (входящие)      site/bank.html (выписка)
        │ /api/cashier/*                     │ /api/sbp/*                  │ /api/bank/*
        ▼                                    ▼                             ▼
   cashier.py ── sell(cash) ──► shelf.sale ──► transactions(income/sale, channel=shelf)
        │        └─► shelf_moves +_register_leg (полка+склад, без двойного счёта)
        │        └─► cashier_sales(method=cash, box_id, request_id)
        │
        ├── sell(sbp) ─► sbp.create(new) + stock.hold(витрина-зона) + shelf.transfer_from_stock
        │                 └─► cashier_sales(payment_id) · cashier_sales не трогает склад
        └── confirm_sbp ─► [снять холд → проверить остатки → shelf.sale(record_income=False)
                            → sbp.confirm → UPDATE cashier_sales.confirmed_at] в одной транзакции

client_bot._paid_notice ─► client_payment_intents(pending) + sbp.create(request_id="client-intent:<id>")
api /api/client-bot/payment ─► sbp.confirm ─► UPDATE client_payment_intents(status=confirmed)

bank_receipts.ingest ─► bank_receipts(external_key) ─► _match(±sbp_match_window_hours, точная сумма)
                       ├─ 1 кандидат + sbp_auto_confirm → sbp.confirm (выручка!)
                       ├─ 1 кандидат, авто выкл → status=matched
                       ├─ >1 кандидата → review
                       └─ нет кандидата → unmatched
sbp.confirm ─► order: acc.add_payment(request_id="sbp:<id>") → payments + transactions(fee из accounts.fee_percent)
           └─ no order: acc.add_transaction(income/sale, channel=sbp) ← fee НЕ пишется
```

Таблицы: `sbp_payments` (23 колонки, `idx_sbp_request` уникальный), `cashier_sales`
(+миграции `cancelled_at, discount_pct, discount_amount, box_id`), `cashier_shifts`
(+`box_id`), `bank_receipts` (уникальный `external_key`), `client_payment_intents`
(+`sbp_id`), `transactions`/`accounts`/`payments`, `shelf_moves`/`shelf_collections`/`reserves(kind=hold|reserve)`.

## 5. Реестр рисков (что нашёл аудит, по убыванию цены ошибки)

| № | Риск | Как воспроизводится | Цена | Что ломает |
|---|---|---|---|---|
| R1 | Импорт выписки глохнет на конфликтной строке и повторяется ошибкой | смоук №8 | остановка сверки на неопределённо долго; поступления не заносятся | отказоустойчивость, касса↔банк |
| R2 | Авто-подтверждение по сумме без доказательства источника | смоук №5 | выдача товара без денег + «оплачено» в отчётах | деньги, доверие |
| R3 | Два независимых контура импорта банка (`/api/bank/*` и `bank_import.apply_rows`) | смоук №6 | двойная выручка → лишний налог (НПД/УСН «доходы»), враньё в P&L | налоги, отчётность |
| R4 | Нет серверных прав на `confirm/reject/refund/link` | смоук №7 | любой гость LAN спишет/вернёт деньги, сотрёт следы | безопасность, кассовая дисциплина |
| R5 | Разрыв «авто-подтвердило → не уведомило → заявка висит pending» | код + `_payment_line` | спорные выдачи, двойная работа, «я оплатил — вы не видите» | UX, репутация |
| R6 | `fee` по СБП пишется только для платежей по заказам, для продаж «с полки» — нет | `sbp.confirm` две ветки | расхождение с банком на 0,x %, занижение расходов на УСН 15% | учёт |
| R7 | Скидка/дарение: `gift` при `discount_pct=100` проходит как продажа 0 ₽ | `cashier.sell` | «увода» товара без денег с отметкой «скидка» | контроль, инвентаризация |
| R8 | `cashier_code` = общий ключ ко всему API кассы; переиспользуется всеми, сессия 12 ч в памяти процесса | `Cashier._sessions` | потеря кода = потеря контроля; рестарт сервера выбрасывает кассира из смены | доступность, аудит |
| R9 | 54-ФЗ: чек не формируется нигде, включая СБП; при этом есть продажи из 1С (`source='1c'`) без сверки наличных | `_shift_totals` (строка `income_1c` «сверяем глазами») | штрафы; расхождение ящика при двойном POS | закон, касса |
| R10 | `_next_number()` = `MAX(CAST(number))+1` без уникального индекса | конкурентные create | дубли номеров платежей в журнале/назначениях | аудит, сверка |
| R11 | 3 устаревших UI-теста и 2 датозависимых теста красные | `python3 -m unittest discover -s connector/tests` | «красный baseline» → новые падения не отличить от старых | процесс |
| R12 | Клиентский request_id живёт в памяти страницы: перезагрузка после успешного ответа → новый ключ | `state.saleRequest` в `cashier.html` | редкий, но реальный двойной чек при «залипшем» ответе | деньги |
