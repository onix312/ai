### Срезы 1–2. Пульт: финал заказа у станка без возврата к ПК

`site/control.html` + `pult.py` + `defect_recovery.py`:
- `last_done` несёт заказ (id/статус) и записанный брак (ключ+название).
- Готовому заказу (status=ready) карточка «Печать закончена» предлагает
  «Выдать»: наличные/долг/«Уже оплачено» — штатным `POST
  /api/order/fulfill` (received+cash, debt, none), СБП — `POST
  /api/sbp/create` на точную сумму остатка (QR, выдача только после
  банк-конфирмы). Неготовому — приёмка (`/api/order/accept`,
  quality_confirmed) и разбор брака: причины со справочника сервера
  (превью `defect_recovery`), комментарий, повтор — только по флагу,
  `request_id` против двойного нажатия.
- Денежный шаг подтверждается одноразовой проверкой кода: новый
  stateless-маршрут `POST /api/cashier/verify` (PIN сотрудника или код
  магазина, без сессии кассы). Сводка пульта несёт price/paid/due —
  деньги считает сервер.
- Стенд pult-check.js: 136 → **147** проверок (сценарии выдачи: код,
  fulfill-пейлоады, СБП-сумма, «Уже оплачено», запрет без кода).

### Срез 3. Касса: вкладка «Заказы» у прилавка

Кассир видит готовые заказы (номер, клиент, телефон, серверный остаток
`economics.debt` — тот же, что в СБП и выдаче пульта), счётчик на
вкладке в общем ритме с «Входящими». Выдача — теми же штатными
маршрутами, что у станка; код заново не спрашивается (кассир вошёл в
кассу кодом). Новых серверных маршрутов нет — вкладка связывает
существующие. Стенд кассы: +5 сценариев; контракт
`CashierOrdersTabTests` (запреты редактирования/очереди/принтера).

### Срез 4. Панель: рабочая слайсер-карточка

Раздел «Печать»: «Свой слайсер Stage 1» перестал быть статусной.
Модель — из библиотеки или с компьютера (новый байтовый маршрут
`POST /api/library/upload`: STL/OBJ, дедупликация по SHA) → план (аудит
без записи) → нарезка (G-code в библиотеку + отчёт) → в очередь явно,
через `/api/jobs/enqueue`, без автостарта; гейты SliceMachine — как
есть. В заголовок G-code добавлены строки сметы в формате Bambu Studio
(`;TIME:`, `;Filament used [g]:`) — задание из нарезки показывает
«≈ время · ≈ граммы», а не пустую смету. Тесты: test_library_upload
(7), SlicerCardTests (4).

### Срез 6. Слайсер ↔ конвейер, пластик со склада

- Карточка слайсера: строка «Для конвейера (FarmLoop)» + циклы +
  катушка со склада (`/api/spools`). Катушка задаёт материал и AMS-слот
  нарезки (сервер подхватывает из бобины, если UI не передал), задание
  получает `spool_id` — расход после печати спишется с этой катушки;
  чужая катушка — 400 до нарезки.
- Нарезка с флагом сразу собирает `.farmloop.gcode`: G-code получает
  проверенный блок снятия с метаданными серии (профиль, цикл, ams,
  материал, id катушки) — «изменение g-кода для фарм-луп».
- «В конвейер (N)» — серия N заданий одной транзакцией
  (`manager.enqueue` с `cycles`, clamp 1..100, source
  printflow-conveyor) + событие в историю конвейера; серия
  продолжается сама (`_maybe_start_next` после снятия детали).
- Фикс: `slicer_auto_postprocess_farmloop` молчал (пустое поле body
  перечитывали вместо настроек). `/api/slicer/profile` отдаёт
  конвейерные гейты (`farmloop_gate`). Тесты: test_slicer_conveyor (11).

### Срез 7. Watch Folder — главный путь

- Статическая карточка Watch Folder в «Печати» (видна всегда): путь,
  вкл/выкл, счётчик; «Включить»/«Выключить»/«Создать папку» — папка
  создаётся с сервера (`POST /api/watch/ensure`), mkdir руками не
  нужен.
- G-code из папки с проверенным FarmLoop-блоком помечается
  (`info["farmloop"]`) — модалка предлагает «В конвейер (N)».
- Катушка со склада в потоке папки: материал из 3MF/G-code →
  `pick_warehouse_spool` (неархивная, с остатком; приоритет — AMS-слот,
  проверенная, больший остаток) → `spool_id` и AMS-маппинг из слота.
- Баг 17.x: `list_pending` не отдавал `fid` — UI открывал первый
  pending, а не кликнутый файл; fid теперь в каждом элементе.
