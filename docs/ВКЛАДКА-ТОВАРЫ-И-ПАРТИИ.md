# Вкладка «Товары» и кнопка «Напечатать партию»

Проект раздела. Документ, а не код: здесь модель данных, экраны, API, порядок работ
и разбор пограничных случаев. Составлено 17 августа 2026 года по фактическому
состоянию репозитория.

---

## 1. Что уже есть и где дыра

В системе сейчас три разных представления одного и того же изделия:

| Где | Таблица | Что хранит | Где в интерфейсе |
| --- | --- | --- | --- |
| База изделий | `catalog` | вес, часы, `fit_per_plate`, цена, материал, файл, ниша | внизу вкладки «Склад пластика» |
| Стеллаж | `shelf_items` | штуки на полке, цена ценника, себестоимость штуки, мин. остаток, фото | вкладка «Стеллаж» |
| Задание печати | `print_jobs` | файл, плита, AMS, граммы, минуты, себестоимость | вкладка «Очередь» |

Связь между ними односторонняя и слабая: `shelf_items.catalog_id` — необязательная
ссылка, `print_jobs` про товар вообще ничего не знает (только `order_id`).

Из-за этого сценарий «напечатать 20 адресников на полку» сегодня выглядит так:

1. открыть «Склад пластика» → найти позицию в базе изделий → посмотреть `fit_per_plate`;
2. в уме или на калькуляторе: `20 / 6 = 4 запуска`;
3. открыть «Принтеры» → «Файлы на принтере» → найти нужный 3MF;
4. четыре раза нажать «Печать» → четыре раза заполнить модалку `print_modal`;
5. дождаться печати, посчитать годные штуки;
6. открыть «Стеллаж» → «+ Приход» → выбрать позицию → выбрать задание из списка →
   вбить количество → проверить, что себестоимость подставилась;
7. повторить пункт 6 ещё три раза (по одному на каждое задание).

Это 15–20 действий и четыре места, где легко ошибиться. При этом **все данные для
автоматизации в базе уже лежат**: `fit_per_plate`, оценка веса и времени из 3MF
(`estimate.py`), себестоимость задания (`accounting.register_job_costs`), приход на
полку (`shelf.produce`), план пополнения (`shelf.items()[].plan_qty`).

Не хватает одной сущности — **партии** — и одного места, где товар виден целиком.

---

## 2. Идея решения одной фразой

> **Товар** — это одна карточка: модель + запас на полке + экономика.
> **Партия** — это «напечатать N штук этого товара», которая сама раскладывается
> на запуски принтера и сама кладёт результат на полку.

Кнопка «Напечатать партию» превращает семь шагов в один диалог и одно нажатие.

## 3. Вкладка «Товары»

### 3.1 Место в навигации

Новый раздел в группе «Экономика», перед «Стеллажом»:

```
Работа        Обзор · Принтеры · Очередь · Заказы · Клиенты
Экономика     Товары ← новое · Финансы · Стеллаж · Склад пластика · Ниши · Калькулятор
Справочник    Библиотека · Настройки
```

Технически: `<a class="nav-link" href="#products" data-view="products">` в `site/index.html`,
`<section class="view" id="view-products">` внутри `#views`, запись в `VIEWS` и
синонимы в `VIEW_ALIASES` (`goods`, `catalog`, `items`) в `site/assets/core.js`.
Тест `connector/tests/test_site_markup.py` требует, чтобы новая секция лежала
внутри `#main > #views` — это единственное структурное ограничение.

«База изделий» из вкладки «Склад пластика» переезжает сюда целиком; на старом месте
остаётся ссылка «База изделий переехала в раздел „Товары“ →», чтобы не ломать привычку.

### 3.2 Что показывает

Товар = строка `catalog` + связанная строка `shelf_items` (если товар лежит на полке).
Карточка сводит воедино то, что сейчас разбросано по трём вкладкам:

```
┌──────────────────────────────────────────────────────────────────────────┐
│  ▦ Товары                                          [⎙ Ценники] [+ Товар] │
│  Модели, запас на полке и экономика — в одном месте                      │

│  KPI: Товаров 14 · На полке 213 шт · Запас 18 400 ₽ · Мало 3 · Печатать 47│
├──────────────────────────────────────────────────────────────────────────┤

├──────────────────────────────────────────────────────────────────────────┤
│ ┌──────────────────────────┐ ┌──────────────────────────┐                │
│ │ [фото] Адресник «Кость»  │ │ [фото] Крючок на стену   │                │
│ │ PLA · 12 г · 0,4 ч · 6/пл│ │ PETG · 34 г · 1,2 ч · 2/пл│               │
│ │                          │ │                          │                │

│ │ [◫ Ценник] [−1] [✎]      │ │ [◫ Ценник] [−1] [✎]      │                │
```

Табличный режим — те же данные строками, с сортировкой по любому столбцу:
`Товар · Материал · г · ч · шт/плита · На полке · Продажи 7д · Хватит на · Цена ·
С/с · Маржа · ₽/час печати · Статус · Действия`.

### 3.3 Статусы товара

Считаются на сервере, как уже сделано в `shelf.items()`:

| Статус | Условие | Цвет |
| --- | --- | --- |
| В наличии | остаток выше минимума | зелёный |
| Мало | `qty <= min_qty` или `days_left < 3` | жёлтый |
| Кончился | `qty == 0`, но продажи были | красный |
| Мёртвый сток | 14+ дней без продаж при `qty > 0` | серо-красный |
| Только модель | есть в `catalog`, на полку не кладём | серый |
| Убыточный | `profit_per_hour < target_profit_per_hour` | контурный красный |

Статус «Убыточный» — новый и важный: он честно отвечает на вопрос «а стоит ли вообще
печатать этот товар», используя уже существующий расчёт `catalog[].economics`.

### 3.4 Кнопка «⎙ Ценники» в шапке

Массовая печать: выбрать позиции на стеллаже → открыть `/price-tags.html`.
Конструктор берёт живые данные, QR и Code 128, а формат каждой позиции хранит
явно: ценник 66 × 31 мм или промостенд 66 × 56 мм.

## 4. Кнопка «Напечатать партию»

### 4.1 Диалог

Открывается из карточки товара, из строки таблицы и из шапки раздела
(тогда товар выбирается в первом поле).

```
┌─────────────────────────────────────────────────────────────────┐
│  Партия печати                                              [×] │
│  Крючок на стену · PETG · 34 г · 1,2 ч · 2 шт на плиту           │
├─────────────────────────────────────────────────────────────────┤
│  Сколько штук нужно      [ 33 ]  ⚑ по продажам за 7 дней        │
│  Режим раскладки         (•) Полные плиты  ( ) Ровно 33  ( ) Вручную│
│  Файл на принтере        [ hook_x2.3mf                       ▾ ] │
│  Принтер                 [ P1S — свободен                    ▾ ] │
│  Катушка                 [ PETG чёрный · 740 г               ▾ ] │
│  Приход на полку         [ Крючок на стену                   ▾ ] │
│  Приоритет в очереди     [ 0 ]    ☑ Стартовать сразу            │
├─────────────────────────────────────────────────────────────────┤
│  РАСЧЁТ                                                          │
│  17 запусков × 2 шт = 34 шт  (плюс 1 шт сверх плана)             │
│  Время печати        20 ч 24 мин   финиш ≈ завтра 11:40          │
│  Пластик             1 156 г       ⚠ на катушке 740 г — не хватит│
│                                    хватит на 21 шт (11 запусков) │
│  Себестоимость       5 032 ₽ · 148 ₽ за штуку                    │
│  Выручка при 540 ₽   18 360 ₽ · прибыль 13 328 ₽ · 653 ₽/час     │
│  ✓ Выгодно: 653 ₽ чистыми за час печати при норме 250 ₽          │
├─────────────────────────────────────────────────────────────────┤
│  ⚠ Пластика хватит на 21 шт. Поставить всю партию в очередь —    │
│    задания сверх остатка подождут новой катушки.                 │
├─────────────────────────────────────────────────────────────────┤
│             [Отмена]  [Только посчитать]  [⎙ Напечатать партию]  │
└─────────────────────────────────────────────────────────────────┘
```

Ключевое: **все цифры пересчитываются на сервере при каждом изменении поля**
(`POST /api/batch/plan`, ничего не пишет в базу). Расчёт использует уже готовые
`accounting.cost_breakdown()` и `accounting.suggest_price()` — новой арифметики
во фронте не появляется, как и в калькуляторе.

### 4.2 Три режима раскладки

Это единственное место, где нужно решение владельца, потому что 3MF на SD-карте
нарезан с фиксированным числом копий на плите.

| Режим | Что делает | Когда применять |
| --- | --- | --- |
| **Полные плиты** (по умолчанию) | `plates = ceil(qty / fit)`, печатаем чуть больше | обычный запас на полку — лишнее не пропадёт |
| **Ровно N** | `plates = floor(qty / fit)`, остаток помечается «нужен отдельный файл» | заказ на точное количество |
| **Вручную** | владелец сам вводит число запусков | нестандартный файл, тестовая печать |

### 4.3 Что происходит по нажатию

```
[⎙ Напечатать партию]
        │
        ├─ 1. Создаётся запись batches (state=planned)
        │
        ├─ 2. В print_jobs добавляется N заданий одним файлом,
        │     у каждого batch_id и batch_qty (сколько штук даёт запуск)
        │
        ├─ 3. Если «Стартовать сразу» и принтер свободен →
        │     manager.start_job() для первого; остальные ждут в очереди
        │     (уже существующий автозапуск auto_queue подхватит следующие)
        │
        ├─ 4. Печать завершилась (manager._on_print_end):
        │        job.state = done  → accounting.register_job_costs() (как сейчас)
        │                          → НОВОЕ: shelf.produce(item_id, batch_qty,
        │                                    job_id=job.id) — приход на полку
        │                                    с себестоимостью из job.cost
        │        job.state = failed → batch.qty_scrap += batch_qty,
        │                             событие «в партии брак, не хватает N шт»
        │
        ├─ 5. batch.qty_done растёт; когда >= qty_planned → state=done,
        │     событие и уведомление в Telegram «Партия готова: 34 шт на полке»
        │
        └─ 6. Если печать провалилась → state=partial и кнопка «Допечатать 4 шт»,
              которая открывает тот же диалог с уже подставленным остатком
```

Важно: **приход на полку делает не фронт, а коннектор**. Даже если браузер закрыт
и печать шла ночью — утром товар уже на полке с правильной себестоимостью.
Это тот же принцип, что и в существующем автоучёте.

### 4.4 Проверки перед стартом

Часть уже реализована в `manager` для очереди — переиспользуем, а не пишем заново:

| Проверка | Источник | Реакция |
| --- | --- | --- |
| Хватит ли пластика | `manager._enough_filament()` | предупреждение + сколько штук выйдет по факту |
| Тот ли материал в AMS | `manager._material_matches()` | предупреждение «в слоте 1 PLA, нужен PETG» |
| Тихие часы | `manager.quiet_now()` | «старт отложен до 08:00» |
| Принтер занят | снапшот | «встанет в очередь, начнётся после текущей печати» |
| Файл не найден на SD | `printer.files.list_files()` | блокировка кнопки + подсказка загрузить 3MF |
| Товар без `fit_per_plate` | `catalog` | считаем 1 шт на плиту и показываем подсказку заполнить |
| Партия убыточна | `catalog[].economics` | жёлтый вердикт «57 ₽/час против нормы 250 ₽» — не блокируем, но говорим прямо |

## 5. Модель данных

### 5.1 Новая таблица `batches`

```sql
CREATE TABLE IF NOT EXISTS batches (
    id TEXT PRIMARY KEY,
    at TEXT,                        -- когда создана
    catalog_id TEXT,                -- модель из базы изделий
    item_id TEXT,                   -- shelf_items.id: куда придёт приход
    name TEXT DEFAULT '',           -- снимок названия на момент создания
    qty_planned REAL DEFAULT 0,     -- сколько штук нужно
    qty_done REAL DEFAULT 0,        -- сколько уже легло на полку
    qty_scrap REAL DEFAULT 0,       -- потеряно на браке
    fit_per_plate INTEGER DEFAULT 1,
    plates INTEGER DEFAULT 1,       -- сколько запусков создано
    mode TEXT DEFAULT 'full',       -- full | exact | manual
    file TEXT DEFAULT '',
    printer_id TEXT,
    spool_id TEXT,
    material TEXT DEFAULT '',
    est_grams REAL DEFAULT 0,
    est_minutes REAL DEFAULT 0,
    cost REAL DEFAULT 0,            -- накопленная фактическая себестоимость
    state TEXT DEFAULT 'planned',   -- planned|printing|partial|done|cancelled
    note TEXT DEFAULT '',
    finished_at TEXT
);
CREATE INDEX IF NOT EXISTS idx_batches_state ON batches(state, at);
```

### 5.2 Две колонки в `print_jobs`

Через существующий механизм догоняющих миграций — `ADDED_COLUMNS` в `db.py`,
данные не теряются:

```python
"print_jobs": [
    ("est_minutes", "REAL DEFAULT 0"),
    ("est_grams", "REAL DEFAULT 0"),
    ("batch_id", "TEXT"),            # к какой партии относится запуск
    ("batch_qty", "REAL DEFAULT 0"), # сколько годных штук даёт этот запуск
],
```

`SCHEMA_VERSION` поднимается до `4`.

### 5.3 Почему не отдельная таблица связи

Один запуск принадлежит ровно одной партии, поэтому таблица `batch_jobs` не нужна —
двух колонок в `print_jobs` достаточно. Это дешевле в миграции и не усложняет
`manager._on_print_end`, где связь и читается.

### 5.4 Товар: `catalog` + `shelf_items`

Сливать таблицы **не нужно** — это дорогая миграция ради косметики. Вместо этого:

- в `catalog` добавляется `shelf_item_id TEXT` (обратная ссылка, для скорости);
- слой `products.py` отдаёт объединённый объект;
- при создании товара во вкладке «Товары» обе записи создаются сразу и связываются;
- «Товар только-модель» = строка `catalog` без пары в `shelf_items`;
- существующие несвязанные позиции стеллажа показываются как «товар без модели»
  с кнопкой «привязать модель» — старые данные не ломаются.

## 6. API

Новый модуль `connector/printflow/products.py` (товары + партии), по образцу `shelf.py`.

### GET

| Маршрут | Ответ |
| --- | --- |
| `/api/products` | `{items: [...], summary: {...}}` — объединённые товары с экономикой и остатком |
| `/api/product?id=` | карточка + история движений + история партий |
| `/api/batches?state=&limit=` | список партий |
| `/api/batch?id=` | партия + её задания + прогресс |

### POST

| Маршрут | Тело | Действие |
| --- | --- | --- |
| `/api/product/save` | поля товара | создаёт/обновляет `catalog` и `shelf_items` в одной транзакции |
| `/api/product/delete` | `{id}` | архивирует модель, позиция стеллажа остаётся с историей |
| `/api/batch/plan` | `{catalog_id, qty, mode, plates?, printer_id, spool_id}` | **ничего не пишет**, возвращает расчёт: плиты, штуки, граммы, часы, ETA, себестоимость, прибыль, ₽/час, предупреждения |
| `/api/batch/create` | то же + `{item_id, start_now, priority}` | создаёт партию и N заданий, при `start_now` запускает первое |
| `/api/batch/start` | `{id}` | запустить следующее задание партии вручную |
| `/api/batch/cancel` | `{id}` | отменить незапущенные задания, партия → `cancelled` |
| `/api/batch/receive` | `{id, qty, scrap?}` | ручная приёмка (печатали мимо системы или часть ушла в брак) |
| `/api/batch/repeat` | `{id}` | повторить партию тем же составом |

Формат ответа `/api/batch/plan` — тот же стиль, что у `/api/calc/cost`:

```json
{
  "plates": 17, "qty_real": 34, "qty_extra": 1,
  "grams": 1156, "hours": 20.4, "eta": "2026-08-18T11:40:00+03:00",
  "cost": {"total": 5032.0, "per_unit": 148.0, "filament": 1849.6, "...": "..."},
  "price": 540, "revenue": 18360, "profit": 13328, "profit_per_hour": 653,
  "verdict": "ok",
  "warnings": [
    {"kind": "filament", "text": "На катушке 740 г — хватит на 21 шт (11 запусков)"}
  ]
}
```

## 8. Порядок работ

**Этап 1 — каркас (полдня).**
Таблица `batches`, колонки в `print_jobs`, `products.py` с `plan()` и `create()`,
маршруты `/api/products`, `/api/batch/plan`, `/api/batch/create`.
Проверяется curl-ом, без интерфейса.

**Этап 2 — автоматика (полдня).**
Хук в `_on_print_end`: приход на полку, учёт брака, закрытие партии, событие
и Telegram. Тест: имитировать завершение задания и проверить, что штуки легли
на полку с правильной себестоимостью.

**Этап 3 — вкладка «Товары» (день).**
Секция, плитки и таблица, KPI, фильтры, карточка товара, перенос базы изделий.

**Этап 4 — диалог партии (полдня).**
Модалка, live-пересчёт, предупреждения, вердикт, кнопки «Только посчитать» и
«Напечатать партию».

**Этап 5 — хвосты (полдня).**
Прогресс партии на «Обзоре» и в «Очереди», «Допечатать N шт», «Повторить партию»,
массовая печать ценников, документация.

Итого около трёх рабочих дней. Этапы 1–2 уже дают пользу через API, этап 4 —
момент, когда кнопка появляется физически.

## 9. Пограничные случаи

| Ситуация | Как ведёт себя система |
| --- | --- |
| Печать сорвалась на 3-м из 17 запусков | `qty_scrap += 2`, партия `partial`, событие «не хватает 2 шт», кнопка «Допечатать» |
| Владелец отменил задание вручную | задание `cancelled` → в `qty_done` не попадает, партия остаётся `partial` |
| Плита вышла с браком, но принтер отчитался «done» | «Приёмка партии»: ввести факт годных → `receive(qty, scrap)`, расхождение в журнал |
| Товар удалили, пока партия печаталась | приход пишется в `shelf_moves` с пометкой «позиция удалена», деньги не теряются |
| Два принтера печатают одну партию | штатно: задания без жёсткой привязки, `printer_id` пустой, берёт любой свободный |
| Файл на SD переименовали | задание падает на старте, партия `partial`, подсказка «выберите файл заново» |
| `fit_per_plate` в базе неверный | приёмка партии позволяет исправить факт; после трёх расхождений — подсказка «обновите шт/плиту, факт стабильно другой» |
| Партия «в запас» при полной полке | предупреждение «на полке уже 40 шт при продажах 2 шт/нед — заморозите 5 900 ₽» |
| Печать шла ночью, браузер закрыт | всё считает коннектор; утром партия закрыта, товар на полке |

## 11. Ещё идеи на эту тему

Пометки трудоёмкости как в `docs/ИДЕИ-АВТОМАТИЗАЦИИ.md`:
⚡ быстро (полдня) · ◐ средне (день) · ▣ крупно (несколько заходов).

### Печать партиями — развитие

**P1. Смешанная плита ◐**
Мелкие товары выгоднее печатать вместе: 4 адресника + 2 брелока на одной плите.
Партия из нескольких товаров, один файл, приход раскладывается по позициям
пропорционально. Экономит нагрев и калибровку — при 20-минутных изделиях это
до 30 % времени плиты.

**P2. Автопартия по плану пополнения ◐**
`shelf.items()[].plan_qty` уже считает, чего сколько не хватает. Кнопка
«Собрать партию по плану» на вкладке «Товары»: система предлагает список
«крючок 33, адресник 12, органайзер 8», владелец снимает галочки и ставит всё
в очередь одним нажатием.

**P3. Ночная смена ⚡**
Флажок «печатать ночью» у партии: задания ставятся с учётом `quiet_hours`, самые
длинные — на ночь, короткие — на день, когда есть кому снять деталь со стола.

**P4. Дозагрузка принтера ⚡**
Принтер освободился, очередь пуста, на полке есть товары со статусом «Мало» →
уведомление «P1S простаивает 40 мин. Напечатать крючки (33 шт нужно)?» с кнопкой
прямо в Telegram. Простой принтера — это чистый убыток по амортизации.

**P5. Экономика партии против розницы ⚡**
В диалоге показывать разницу: «партией 34 шт — 148 ₽/шт, поштучно — 197 ₽/шт,
экономия 1 666 ₽». Наглядно объясняет, зачем вообще печатать партиями.

**P6. Резерв катушки под партию ◐**
При создании партии «занять» нужные граммы на катушке, чтобы другая печать их не
съела. Остаток показывается как «740 г, из них 620 г зарезервировано».

**P7. Очередь по дедлайну полки ◐**
Приоритет заданий считается не вручную, а из «хватит на N дней»: товар, который
кончится через 2 дня, обгоняет тот, которого хватит на две недели.

### Товары — развитие карточки

**T1. Себестоимость по факту, а не по нормативу ⚡**
У товара накапливается история партий. Показывать «норматив 34 г, факт в среднем
37,2 г (+9 %)» и предлагать обновить карточку. Данные уже пишутся в `print_jobs`.

**T2. Варианты товара ◐**
Один товар — несколько цветов и размеров. Сейчас это отдельные позиции, и полка
захламляется. Родитель + варианты: общая модель и экономика, отдельные остатки.

**T3. Комплекты ◐**
«Набор органайзеров = 3 разных детали». Продаётся как один товар, печатается как
партия из трёх позиций, списывается комплектом. Перекликается с идеей A4
из `ИДЕИ-АВТОМАТИЗАЦИИ.md`.

**T4. Фото из камеры принтера ⚡**
Кнопка «снять фото товара» берёт кадр с камеры по окончании печати —
`camera.snapshot()` уже есть, фото хранится в `shelf_items.photo`.

**T5. Карточка для Авито в один клик ⚡**
Из товара собирается готовый текст объявления: название, материал, размеры, цена,
условия. Копируется в буфер. Стиль и формулировки — из `docs/ГОТОВЫЕ-ПОСТЫ.md`.

**T6. История цены товара ⚡**
`price_history` уже существует для заказов. Расширить на товары: график цены и
подсказка «подняли цену на 12 % — продажи не упали, можно ещё».

**T7. ABC-анализ прямо в списке ⚡**
`accounting.abc_report()` готов. Метка A/B/C у каждого товара: 20 % позиций дают
80 % прибыли, остальное имеет смысл убрать с полки.

**T8. Сезонность ◐**
Продажи по месяцам за год: «этот товар берут с ноября по февраль». Подсказка
«начните печатать запас за 3 недели до сезона».

**T9. Штрихкод и печать этикеток ◐**
QR уже генерируется. Добавить линейный код для кассы магазина, чтобы 1С сверялась
с PrintFlow без ручного сопоставления названий.

**T10. Ссылка «модель» ⚡**
Поле с URL модели (свой CAD-файл, Printables, коммерческая лицензия) прямо в
карточке. Сейчас лицензии проверяются по памяти, а это правовой риск из
`PROMPT-ДЛЯ-ИИ.md`.

### Полка и продажи

**S1. Экран инвентаризации на телефон ⚡**
`shelf.html` уже открывается по QR. Режим «пересчёт»: список товаров с полем факта,
одна кнопка «Сохранить» → все расхождения разом.

**S2. Продажа по скану ⚡**
Покупатель или продавец сканирует QR ценника → «Купил 1 шт» → списание. Страница
позиции для этого уже готова, нужен только режим киоска.

**S3. Уценка мёртвого стока ⚡**
Товар без продаж 14+ дней: кнопка «Уценить на 20 %» — меняет цену, перепечатывает
ценник, пишет событие. Замороженные деньги лучше вернуть дешевле, чем не вернуть.

**S4. «Что положить на полку завтра» ⚡**
Утренний дайджест в Telegram уже отправляется. Добавить строку: «Полка: кончились
крючки, мало адресников. В очереди 2 партии, готовы к 14:20».

**S5. Прибыль на сантиметр полки ◐**
Полка конечна. Если у товара есть габарит, считать «₽ прибыли на см² полки в месяц»
и предлагать заменить неэффективные позиции.

### Аналитика партий

**A1. Отчёт «Партии за месяц» ⚡**
Сколько партий, штук, часов, брака, средняя себестоимость. Тренд брака по товарам —
прямой сигнал, где чинить модель или профиль печати.

**A2. План/факт по времени ⚡**
Оценка из 3MF против реального времени. Систематическое расхождение — повод
поправить норматив, а не удивляться срыву сроков.

**A3. Стоимость простоя ⚡**
Часы, когда принтер был свободен, а на полке был дефицит, × 250 ₽/час нормы =
«упущено 3 400 ₽ за неделю». Мотивирует не оставлять принтер пустым.

**A4. Прогноз «когда кончится» ▣**
По скорости продаж — дата, когда каждый товар обнулится, на одной шкале времени.
Партии ставятся так, чтобы дефицита не было ни в один день.
