# Verification Engine 1.0

Task Engine больше не считает `ok=true` достаточным доказательством того, что
внешний мир действительно изменился.

После успешного skill NOZZA вызывает независимый verifier:

```text
execute
  ↓
skill says ok
  ↓
observe state
  ↓
verify
  ├─ verified → следующий шаг
  ├─ assumed  → следующий шаг, но честно помечаем отсутствие доказательства
  └─ failed   → остановить задачу
```

## Статусы

### verified

Есть независимое чтение состояния после действия и оно совпадает с ожидаемым.

### assumed

Skill сообщил успех, но надёжной независимой проверки для него пока нет или
состояние нельзя прочитать на этой машине.

Это **не** отображается как verified.

### failed

Удалось прочитать состояние и оно явно не совпало. Task Engine ставит текущий
шаг и всю задачу в `failed`, следующий шаг не запускается.

## Verifier 1.0

Независимая проверка сейчас есть для:

- `system.volume` — уровень/mute читаются обратно через Core Audio;
- `window.focus` — сверяется фактически активное окно;
- `clipboard.write` — текст читается обратно из clipboard.

Остальные навыки пока получают `assumed`. Это намеренно лучше, чем ложный
зелёный статус.

## Safety

Verifier никогда не повторяет исходное действие. Он только читает состояние.

Если verification сама недоступна или падает, результат становится `assumed`,
а не `failed`, чтобы отсутствие диагностического канала не превращалось в
ложную ошибку.

Только **явное несоответствие** даёт `failed`.

## Confirmed actions

Шаги, которые требуют confirmation, проверяются после того, как человек нажал
«Разрешить» и реальный skill завершился. Только после verification Task Engine
может перейти к следующему шагу.

## Persistence

Verification сохраняется внутри `result_json` каждого task step:

```json
{
  "_verification": {
    "status": "verified",
    "reason": "Активное окно совпадает",
    "evidence": {"active": "Telegram"}
  }
}
```

Отдельная миграция SQLite не нужна. API дополнительно возвращает удобное поле
`step.verification`.

## Native UI

Control Center показывает агрегат по задаче, например:

```text
Проверка: verified 2 · assumed 1
```

Если verifier остановил задачу, причина остаётся в поле ошибки задачи.

## Следующий этап

Verification 2.0 может добавить специализированные проверки для:

- `app.open`;
- файловых операций;
- браузерных действий;
- PrintFlow-команд;
- процессов и сервисов.

Там, где проверка требует ожидания внешнего события, понадобится retry/polling
с ограниченным timeout, а не один мгновенный read.
