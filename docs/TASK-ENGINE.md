# Task Engine 1.0

Task Engine превращает понятные многошаговые команды NOZZA в долговечные задачи.

## Зачем

Раньше цепочка вроде:

```text
громкость 30 и следующий трек
```

исполнялась Brain по шагам в рамках одной реплики. Если один из шагов требовал
подтверждения, следующие шаги могли быть уже запущены. Task Engine меняет модель:

```text
goal
  ↓
step 1 → execute → verify result
  ↓
step 2 → confirmation? → WAIT
  ↓                         │
step 3 ← continue ← human ──┘
  ↓
DONE
```

## Инварианты безопасности

- Task Engine не имеет собственного способа выполнять системные действия.
- Каждый шаг обязан существовать в `agent/skills.py`.
- Параметры проходят тот же `skills.check_params`.
- Исполнение идёт только через `Agent.run_skill`.
- Если обычный навык требует подтверждения, задача переходит в `waiting`.
- Следующий шаг не запускается до решения человека.
- Отмена подтверждения ставит задачу на паузу.
- Истёкшее подтверждение тоже переводит задачу в `paused`, а не оставляет
  вечный `waiting`.

## Persistence

Задачи хранятся в собственной SQLite ассистента:

- `assistant_tasks`
- `assistant_task_steps`

Хранятся цель, статус, текущий шаг, параметры навыка, результат и pending action.

После перезапуска NOZZA незавершённые `running/waiting` задачи не продолжаются
автоматически. Они переходят в `paused` с объяснением. Это намеренно: процесс
мог умереть после реального side effect, но до записи результата, поэтому
автоматический повтор был бы опасен.

## Статусы

Задача:

- `planned`
- `running`
- `waiting`
- `paused`
- `failed`
- `done`
- `cancelled`

Шаг:

- `pending`
- `running`
- `waiting`
- `failed`
- `done`
- `cancelled`

`failed` задача не перезапускается молча. Повтор/repair будет отдельной
операцией следующего слоя планировщика.

## Brain

Task Engine используется только для цепочек, которые Brain уже смог разобрать в
конкретные зарегистрированные навыки. Если один из шагов не понятен, сохраняется
старый путь уточнения/модели.

Это важная граница: Task Engine отвечает за надёжное исполнение плана, а не за
выдумывание плана.

## API

Agent port, обычно `127.0.0.1:8799`:

```text
GET  /tasks?limit=50&status=
POST /tasks
```

Операции POST:

```json
{"op":"create","title":"Рабочий режим","goal":"Подготовить ПК","start":true,
 "steps":[
   {"skill":"system.volume","params":{"level":30}},
   {"skill":"system.media","params":{"action":"play_pause"}}
 ]}
```

Также: `run`, `pause`, `resume`, `cancel`, `get`, `list`.

## Native UI

Раздел «Задачи» показывает:

- название и статус;
- прогресс N/M;
- причину паузы/ошибки;
- «Запустить / Продолжить»;
- «Пауза»;
- «Отменить задачу»;
- отдельные карточки подтверждения существующей safety-очереди.

## Следующий слой

Task Engine 1.0 исполняет уже понятный план. Следующий этап, Planner 1.0, сможет
строить такой план из более общей цели, но всё равно будет ограничен тем же
реестром навыков и policy/confirmation слоем.


## Verification

После `Agent.run_skill` успешный шаг проходит отдельный post-action verifier.
Task Engine различает:

- `verified` — фактическое состояние прочитано и совпало;
- `assumed` — skill сообщил успех, но независимого доказательства нет;
- `failed` — состояние прочитано и явно не совпало.

`failed` блокирует переход к следующему шагу. Подробности:
[VERIFICATION.md](VERIFICATION.md).
