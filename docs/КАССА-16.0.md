# Касса 16.0 — трекер решений и состояния

> Проект: клиентский бот, мобильная касса по LAN, оплата по СБП.
> Заказчик: владелец PrintFlow. Исполнитель: Arena-агент.
> Главное требование: **деньги не должны ломаться** — каждая оплата (наличная или
> СБП) — платёж с основанием, попадает на правильный счёт, не дублируется,
> отменяется/возвращается явно и виден в журнале.
> Процесс: раунды вопросов → ТЗ → итерации → отчёты → приёмка.

## ТЗ на первый релиз (16.0.0)

### Входит в v1

**Итерация 1 — СБП-ядро (деньги):**
1. Платёж со статусами `new → pending → confirmed / rejected / refunded`
   (расширяем существующий `client_payment_intents` или отдельная сущность
   `sbp_payments` — решим в итерации, без ломки текущего).
2. Статический QR магазина (владелец загружает картинку/строку QR в настройки)
   + динамический QR/ссылка на сумму конкретного заказа.
3. Экран «Входящие платежи»: список `pending`, кнопки «Подтвердить»/«Отклонить»
   (ручное подтверждение в v1).
4. Подтверждение → платёж пишется в журнал транзакций на счёт СБП
   (настраиваемый), закрывает долг заказа, разблокирует выдачу.
5. Идемпотентность: двойное нажатие/обновление страницы не создаёт второй
   платёж (`request_id`).
6. Отклонение неподтверждённого платежа — без тихих правок, в аудите.
7. Возврат СБП — только руководитель/владелец, отметка «возврат выполнен
   в банке», с аудитом и проводкой (refund).
8. Аудит каждого действия: кто, когда, заказ, сумма.

**Итерация 2 — мобильная касса PWA в LAN:**
9. Вход по общему коду магазина (настройка владельца).
10. Продажа с полки в 3–4 касания: товар → способ оплаты (наличные/СБП) →
    подтверждение.
11. Наличные — как сейчас (`in_shop`); СБП — создаёт платёж со статусом,
    подтверждается кассиром.
12. Просмотр остатков.
13. Без смен в v1 — продажи сразу в журнал.
14. Работает в LAN без интернета; наружу только СБП (отключаемо настройкой).
15. Роли: кассир (employee) — продажи; руководитель — деньги/возвраты;
    владелец — всё (права из `staff.py` распространяем на кассу и API).

**Итерация 3 — клиентский бот:**
16. Ссылка/QR на оплату СБП в чате + статус «ожидает оплаты» → «оплачено».
17. Платёж привязан к заказу: подтверждение → долг закрыт → выдача
    разблокирована.
18. Уведомления «оплачено / готово».

**Общий контур (связка):**
19. Платёж подтверждён → долг закрыт → заказ/выдача разблокированы.
20. Один учёт: склад/полка/заказ/деньги/бот не дублируются и не расходятся.

### НЕ входит в v1

- Авто-подтверждение СБП через банк/вебхук (отдельный раунд).
- Фискальный чек (54-ФЗ) — только запись в журнале.
- Нативное мобильное приложение.
- Программа лояльности / история заказов клиента.
- Офлайн-кэш с дозаписью (касса работает в LAN, без кэша вне сети).
- Смены с X/Z-отчётами.

### Приёмка (сценарии)

1. **СБП-платёж:** от создания QR/ссылки до подтверждения — деньги на счёт СБП,
   долг закрыт, заказ выдаётся; двойное нажатие не дублирует; отказ и возврат —
   с аудитом, без «мусора» в отчётах.
2. **Касса на телефоне:** кассир в LAN продаёт с полки за наличные и по СБП,
   видит остатки; при отключённом интернете продажа работает, СБП/Telegram —
   отключаются.
3. **Клиентский бот:** клиент получает ссылку, платит, видит «ожидает оплаты»;
   после подтверждения — «оплачено», заказ разблокирован.

### Критерии готовности

- `pytest`, `py_compile` по всем изменённым модулям, `node --check` по JS.
- Живой смоук через API и LAN-страницы.
- Версия `APP_VERSION = 16.0.0`, запись в `CHANGELOG.md`, отчёт в чат.

## Раунд «авто-СБП» — решения заказчика (2026-09-06)

- Направление: авто-подтверждение СБП через банк/вебхук; v1 принят.
- Банк: Т-Банк; API-токена пока нет.
- Источник: сейчас импорт выписки Т-Банка (CSV); API-поллинг — позже; вебхук
  отложен (нет публичного адреса для LAN).
- Сопоставление: сумма + окно времени + ожидающий платёж.
- Правило: строгое — авто только при точном совпадении; иначе «на сверку» с причиной.
- Несопоставленные: в очередь «на сверку» (не игнорируем, не уведомляем).
