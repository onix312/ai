# PrintFlow без LAN Only Mode — управление через Bambu Cloud

**Дата:** 19.08.2026 (UTC) — PrintFlow 8.1, парк 1× P1S + AMS
**Задача:** сделать всё, что PrintFlow умеет с принтером (мониторинг, команды,
загрузка файлов, запуск печати, камера, очередь, автоучёт), **не включая на
принтере LAN Only Mode / Developer Mode** — принтер остаётся в обычном облачном
режиме, Bambu Handy и Bambu Studio продолжают работать как раньше.

**Статус: РЕАЛИЗОВАНО в 8.1.** Ниже — план (исходный) и замечания, как он
воплощён в коде.

**Ответ коротко:** перейти с локального MQTT (принтер:8883) на **облачный
MQTT-брокер Bambu** (`us.mqtt.bambulab.com:8883`) + **HTTP API Bambu Cloud**
(`api.bambulab.com`) для входа, списка принтеров, загрузки 3MF и истории печати.
Формат сообщений MQTT у облака **тот же**, что у локального принтера — весь
существующий код телеметрии и команд переиспользуется почти без изменений.
LAN-протоколы остаются как опциональный «локальный ускоритель» (камера, SD-карта),
но без них можно жить.

## 1. Почему LAN Only Mode мешает

Что происходит сейчас (по коду и докам репозитория):

- `bambu.py` ходит на **локальный** MQTT `{host}:8883`, логин `bblp` + Access Code.
- На прошивках **01.07.00+** Bambu закрыл локальный MQTT/FTPS для сторонних
  программ: команды отклоняются (`reason_code != 0`, HMS `0500-0500-0001-0007`
  «MQTT command verification failed», код 84033543).
- Обходной путь, который сейчас описан в репозитории — включить на принтере
  **LAN Only Mode + Developer Mode**. Но это выключает Bambu Cloud и Bambu Handy:
  пропадают печать с телефона, история, уведомления Handy и связка с аккаунтом.
- Получается выбор «или PrintFlow, или Bambu Handy» — а хочется «и то, и то».

Из исследования (см. §3): **облачный путь этого противоречия не имеет.**
Принтер в обычном облачном режиме держит собственное зашифрованное соединение
с брокером Bambu; клиент, вошедший в тот же аккаунт Bambu, шлёт команды на тот
же брокер — и принтер их принимает, потому что это тот самый канал, которым
пользуется Bambu Handy. Это официально использует интеграция Home Assistant
(Bambu Lab / pybambu): в облачном режиме работают мониторинг и управление,
LAN нужен только для камеры и отправки файлов на SD.

## 2. Что выяснило исследование протоколов Bambu Cloud

Сводка по открытым источникам (OpenBambuAPI, pybambu/Home Assistant,
coelacant1/Bambu-Lab-Cloud-API, open-bambu-networking), состояние на 08.2026.

### 2.1 Облачный MQTT-брокер — главный канал

| Параметр | Значение |
|---|---|
| Адрес (Global) | `us.mqtt.bambulab.com:8883` (TLS) |
| Адрес (China) | `cn.mqtt.bambulab.com:8883` |
| Логин | `u_{user_id}` — id аккаунта с префиксом `u_` |
| Пароль | `accessToken` аккаунта (целиком, без префиксов) |
| Топики | те же, что в LAN: `device/{serial}/report` (читать), `device/{serial}/request` (писать) |
| Протокол | MQTT 3.1.1, JSON |

Ключевое: **все команды и вся телеметрия — в том же формате, что уже разбирает
`bambu.py`**. `pushall`, `get_version`, `pause/resume/stop`, `ledctrl`,
`print_speed`, `gcode_line`, `ams_filament_setting`, `project_file` — всё работает
через облако так же, как через LAN. Меняется только адрес брокера и пара
логин/пароль.

### 2.2 HTTP API `https://api.bambulab.com/v1`

Авторизация — `Authorization: Bearer {accessToken}`. Полезные endpoint'ы:

**Вход (login):**
```
POST /v1/user-service/user/login
{ "account": "<email>", "password": "<password>" }
→ { "accessToken": "...", "loginType": "" }            # сразу токен, либо
→ { "loginType": "verifyCode" }                        # нужен код с почты/SMS
→ { "loginType": "tfa", "tfaKey": "..." }              # нужен 2FA-код
```
Второй шаг (если пришёл `verifyCode`): `POST /v1/user-service/user/login`
с `{ "account": "<email>", "code": "<код из письма>" }` → `accessToken`.
Запросить код: `POST /v1/user-service/user/sendemail/code` (или SMS-вариант).
Токен живёт ~3 месяца; refresh-эндпоинт на практике отдаёт 401 — при истечении
просто логинимся заново тем же способом.

Важно: API за Cloudflare — нужны «слайсерные» заголовки, иначе 403:
`X-BBL-Client-Type: slicer`, `X-BBL-Client-Version`, `X-BBL-Agent-Version`,
`X-BBL-OS-Type` и т.п. (полный набор pybambu шлёт как `bambu_network_agent`).
Как страховка — опциональная зависимость `cloudscraper`/`curl_cffi`, без них
работает обычный `urllib` (стандартная библиотека — требование репозитория).

**ID аккаунта (нужен как `u_uid` для MQTT):**
```
GET /v1/design-user-service/my/preference → { "uid": 123456789, ... }
```
(Раньше uid был внутри JWT-токена, теперь — только этим запросом.)

**Список принтеров аккаунта (замена/дополнение SSDP-поиска):**
```
GET /v1/iot-service/api/user/bound
→ { "devices": [ { "dev_id": "<serial>", "name": "Bambu P1S",
                   "online": true, "print_status": "RUNNING",
                   "dev_product_name": "P1S", "dev_model_name": "C12",
                   "dev_access_code": "<LAN access code!>" } ] }
```
Приятный бонус: облако отдаёт и **LAN Access Code** — можно автоматически
заполнить карточку принтера и сразу включить локальные ускорители (камера/FTPS)
без ручного переписывания кода с экрана.

**История печатей (заполнение журнала PrintFlow):**
```
GET /v1/user-service/my/tasks?deviceId=<serial>&limit=20
→ { "hits": [ { "title", "cover", "status", "startTime", "endTime",
                "weight", "costTime", "plateIndex", "deviceId", "mode",
                "amsDetailMapping": [ { "filamentType": "PLA", "weight": 34.6 } ] } ] }
```
`startTime/endTime` дают фактическую длительность, `cover` — фото результата
(для карточки заказа), `amsDetailMapping` — реальный расход по материалам.
Это закрывает дыры в журнале, когда печать стартовала из Handy/Studio.

**Загрузка 3MF в облако (путь Bambu Studio «печать через облако»):**
```
1. POST /v1/iot-service/api/user/project
   → { project_id, model_id, profile_id, upload_url, upload_ticket }
2. PUT <upload_url>                    # маленький «конфиг» 3mf
3. GET  /v1/iot-service/api/user/upload?models=<model_id>_<profile_id>_<plate>.3mf
   → второй presigned URL
4. PUT <второй URL>                    # основной 3mf с gcode плит
5. PATCH /v1/iot-service/api/user/project/<project_id>   # URL файла
6. POST /v1/user-service/my/task       # запись о задании (для истории Handy)
7. MQTT project_file с url = presigned https-ссылкой   # принтер качает сам
```

### 2.3 Подпись команд на новых прошивках (главный риск — честно)

- Стоковая прошивка 01.08+ вне Developer Mode отклоняет **неподписанный**
  `project_file` для .3mf (HMS 84033543 «MQTT Command verification failed»).
  Обычные команды (пауза/стоп/свет/скорость/температуры/gcode) через **облачный**
  брокер проходят — это тот же канал, что у Handy.
- Надёжный обход для запуска печати без подписи: **слайсить в .gcode**
  (Bambu Studio: «Export G-code»), класть на принтер по FTPS (в облачном режиме
  FTPS-заливка работает) и стартовать командой `print.gcode_file` — она в набор
  «привилегированных» не входит.
- Полная облачная цепочка (шаги 1–7 из §2.2) воспроизводит путь Bambu Studio;
  на части прошивок принтер принимает её и без Dev Mode. Если принтер отвечает
  отказом — PrintFlow честно говорит об этом и предлагает два готовых запасных
  пути (§6.4), а не требует включать LAN Only.

### 2.4 Что остаётся локальным (и это ок)

- **Камера** (порт 6000): работает в обычном облачном режиме с Access Code —
  её новые прошивки не трогали (HA в облачном режиме так и делает: облако для
  данных + локальный IP для камеры). LAN Only не нужен.
- **FTPS (990) / список файлов SD**: LAN-штука; в облачном режиме доступна,
  если компьютер в одной сети с принтером. Удаление файлов по облаку не
  существует в принципе — поэтому в облачном режиме вкладка «Файлы» показывает
  облачные файлы (загруженные проекты), а SD-вкладка появляется, когда FTPS
  отвечает.

## 3. Архитектура решения

Один принтер получает поле **`mode`** (режим связи):

| mode | Смысл | Требования |
|---|---|---|
| `cloud` *(новый, по умолчанию для новых принтеров)* | всё через Bambu Cloud | аккаунт Bambu, принтер привязан к аккаунту, принтер **НЕ** в LAN Only |
| `lan` *(текущее поведение)* | локальный MQTT 8883 | IP + Access Code (+ Developer Mode на новых прошивках) |
| `auto` | пробуем LAN → при неудаче облако | оба набора полей |

Три новых/изменённых модуля:

```
connector/printflow/
├── bambu_cloud.py      # NEW: сессия аккаунта Bambu Cloud
│   ├── login(email, password, region) → token (verifyCode/TFA-шаги)
│   ├── uid(), devices(), tasks(serial), upload_project(3mf) → (project_id, url)
│   └── хранение токена в settings (SECRET_SETTINGS, как telegram_token)
├── bambu.py            # BambuPrinter: параметризация транспорта
│   └── mode: lan → (host:8883, bblp, access_code)
│        cloud → (us.mqtt.bambulab.com:8883, u_uid, accessToken) через CloudBridge
└── (новое) cloud_bridge.py  # один paho-клиент на аккаунт, раздача по serial
```

**CloudBridge — одно облачное соединение на аккаунт.** У Bambu один MQTT-клиент
на аккаунт может обслуживать все принтеры аккаунта (подписка
`device/+/report` или по одному топику на принтер). Bridge подписывается на
`report`-топики всех облачных принтеров и раздаёт сообщения их `BambuPrinter`
по serial из топика. `publish` идёт через тот же клиент. Это экономит соединения
и гарантирует, что PrintFlow не конфликтует с самим собой при нескольких
принтерах. (Bambu Studio/Handy подключаются к брокеру независимо — конфликта
логинов нет.)

`BambuPrinter` в облачном режиме:
- `connect()` → регистрируется в Bridge (вместо своего сокета);
- `publish()` → Bridge.publish(serial, payload);
- `_on_message` → та же нормализация, те же события, **без изменений**;
- `start_print()` → в облачном режиме шлёт `project_file` с `url` =
  presigned-ссылка на 3MF в облаке (или `file://` для файла, который уже на SD
  и залит по FTPS — тогда поведение как сейчас);
- ошибки подключения меняют текст: «не тот Access Code» → «проверьте вход в
  аккаунт Bambu», а «включите LAN Only + Developer Mode» остаётся **только** в
  режиме `lan` как подсказка-фолбэк.

**Fallback-матрица (чем запускаем печать):**

| Условие | Путь запуска | Команда |
|---|---|---|
| Облако, 3MF, прошивка принимает облачную печать | Cloud upload (§2.2, шаги 1–7) | `project_file` + presigned URL через cloud MQTT |
| Облако, есть LAN, 3MF отклонили | FTPS-заливка 3MF + `project_file` с `ftp://` URL через cloud MQTT | как сейчас, но MQTT — облачный |
| Облако, есть LAN, нужен гарантированный путь | Export **.gcode** из Studio → FTPS → `print.gcode_file` | без подписи, работает на стоковой прошивке |
| Облако, LAN нет, принтер отклонил | Файл уже в облаке → подсказка «1 клик в Bambu Handy» | PrintFlow продолжает мониторинг и автоучёт, печать стартовал Handy |
| LAN + Developer Mode (как сейчас) | FTPS + `project_file` на локальный MQTT | текущее поведение, ничего не ломается |

Очередь, preflight, автоучёт и Telegram **не зависят от транспорта**: они живут
на событиях `start/complete/error`, которые приходят одинаково из любого режима.

## 4. Пофайловый план изменений

(Изучены все файлы репозитория; ниже — только те, которых касается фича.)

### 4.1 Новые модули

**`connector/printflow/bambu_cloud.py`** (~400 строк, stdlib-only)
- `login(email, password, region="global", code=None)` → dict(status, token | need_code | need_tfa, message). Шаги verifyCode/TFA из §2.2; заголовки «слайсера»; таймауты; понятные ошибки (Cloudflare → «попробуйте ещё раз», неверный пароль → точный текст).
- `get_uid(token)`, `get_devices(token)` (парсинг §2.2), `get_tasks(token, serial, limit)`.
- `upload_project(token, local_3mf, plate_count)` → 6 шагов §2.2; ретраи PUT; возвращает `{project_id, task_id, url}`.
- Токен/почта/регион — в `settings` через `SECRET_SETTINGS` (там же, где `telegram_token`): ключи `cloud_email`, `cloud_password`, `cloud_token`, `cloud_uid`, `cloud_region`. Пароль храним, потому что перелогин по коду без него невозможен; в UI он закрыт «••••••••» как остальные секреты, в бэкап браузера не попадает.

**`connector/printflow/cloud_bridge.py`** (~200 строк)
- Один `paho-mqtt`-клиент на аккаунт: `connect(token, uid, region)`, `attach(serial, on_message)`, `detach`, `publish(serial, payload)`, backoff-реконнект (как в `bambu.py` `_watch`), событие «облако недоступно» в журнал.
- Кэш `raw` по serial — Bridge держит последний `print`-объект, чтобы переподключение не теряло состояние (P1 шлёт только дельты).

### 4.2 Изменяемые модули

**`connector/printflow/bambu.py`**

- `_on_connect` ошибки: для облака тексты про аккаунт/токен, событие `need_cloud_login` (вместо `need_developer_mode`).

- `snapshot()`: без изменений (плюс поле `connection.mode`).
- `health()`: для облака проверяет bridge.connected + login-статус; для LAN — порты как сейчас.

**`connector/printflow/db.py`**

- `SECRET_SETTINGS` в `config.py`: + `cloud_email, cloud_password, cloud_token, cloud_uid`.

**`connector/printflow/repo.py`**
- `save_printer`: принимать `mode`; маска `access_code` уже есть.
- `printers()`: отдавать `mode`.

**`connector/printflow/manager.py`**
- `reload()`: без изменений (BambuPrinter сам выберет транспорт).
- Новый метод `sync_cloud_history(printer_id)`: раз в N минут/по событию тянет `tasks` из облака и дописывает в `print_jobs` пропущенные завершённые печати (те, что стартовали из Handy): `name, started_at, finished_at, grams=weight, duration=endTime-startTime, state`. - `_maybe_start_next` / очередь: без изменений — события те же.

**`connector/printflow/api.py`**
- `GET /api/printer/discover` → + ключ `cloud`: если аккаунт вошёл — `bambu_cloud.get_devices()` (serial, имя, модель, online, **access_code для автозаполнения**).
- `POST /api/printer/save` → принимает `mode`.
- `POST /api/printer/upload` (`handle_upload`): в облачном режиме, кроме сохранения в `UPLOAD_DIR`, вызывает `upload_project` и кладёт в `print_jobs.file`/ответ `cloud_url`, `project_id`; прогресс — те же события `upload_progress` (считаем байты PUT). Если облако недоступно, а FTPS-порт отвечает — прозрачный фолбэк на текущий путь.
- `POST /api/printer/print` → пробрасывает `cloud_url` в `start_print`.
- Новые: `POST /api/cloud/login` (email/password/region), `POST /api/cloud/code` (verifyCode), `GET /api/cloud/status`, `POST /api/cloud/logout`, `POST /api/printer/sync-history`.
- `GET /api/printer/files`: в облачном режиме без FTPS → `{"cloud": [...список проектов...]}`; UI сам решит, что показать.

**`connector/printflow/network.py`** — диагноз для `mode=cloud` не сканирует порты, а показывает `cloud.connected`, статус логина и `devices`; порты 8883/990/6000 остаются для LAN-режима и «локальных ускорителей».

**`connector/printflow/preflight.py`** — добавить блокер «облачная загрузка не завершена» (нет `cloud_url` у задания в облачном режиме) и warn «принтер не в сети — печать уйдёт через облако».

**`connector/printflow/estimate.py`, `watch_folder.py`, `scripts/printflow_post.py`** — не меняются: оценка и авто-импорт работают с локальным файлом до отправки.

**`connector/printflow_connector.py`, `pf.py`, `launcher_window.py`** — в `doctor` и консольный вывод добавить блок «Bambu Cloud: вход ✓ / не выполнен», иначе без изменений.

### 4.3 Интерфейс (`site/assets/`)

**`app.js` (Настройки)** — секция «Bambu Cloud»: email, пароль, регион
(Global/China), кнопка «Войти», шаг «введите код из письма», статус
«✓ Подключено · 2 принтера». Токен наружу не отдаётся (маска «••••••••», как у Telegram).

**`printer.js` (карточка принтера)**
- Селектор «Связь: ☁ Облако / 🏠 Локальная сеть / Авто» в форме принтера.
- Кнопка «Найти принтеры» → вкладка «Облако» со списком устройств аккаунта — добавление в 1 клик (serial/имя/модель/Access Code приходят сами).
- Бейдж в шапке карточки: `☁ Облако ✓` или `🏠 LAN ✓` (вместо совета про Developer Mode).
- Вкладка «Файлы»: облачные проекты (имя, размер, дата) + превью; SD-карта — если FTPS отвечает.
- Модалка печати: в облачном режиме пункт «отправить через облако» по умолчанию; при отказе принтера — тост с тремя вариантами (§6.4).

**`КАК-ЗАПУСТИТЬ.txt`, `README.md`** — переписать блок «Первое подключение»:
главный путь — аккаунт Bambu Cloud; LAN Only + Developer Mode — опциональный
режим для тех, кто сознательно хочет всё локально.

## 5. Сценарии пользователя

**Первая настройка (было 6 шагов, станет 2):**
1. Настройки → Bambu Cloud → email + пароль → «Войти» (при необходимости — код из письма).
2. Принтеры → «＋ Принтер» → «Облако» → выбрать свой P1S → «Добавить». IP, serial и Access Code заполняются сами.

**Запуск печати (без LAN Only):**
1. Bambu Studio: `Slice → Export 3MF` (или Watch Folder / post-processing скрипт — уже работает).
2. PrintFlow: перетащить файл → оценка + превью + preflight (как сейчас).
3. «Печать» → облачная заливка → `project_file` через облако → принтер качает и печатает.
4. Камера (если компьютер в той же сети), Telegram-уведомления, автоучёт — как раньше.

**Ночь / уехал:** облачный MQTT работает из любого места с интернетом —
мониторинг, пауза, стоп, запуск из очереди. Камера удалённо — только через
Handy (облачный видеопоток — проприетарный TUTK, не копируем; см. §8).

**Печать стартовал Handy:** PrintFlow видит её через облако (те же события),
дополняет журнал из облачной истории (вес, время, фото) и ведёт автоучёт.

## 6. Фолбэки запуска печати (подробно)

**6.1 Облачная печать (основной путь).** Шаги §2.2. Принтер качает 3MF с S3
Bambu сам — по своему облачному каналу, без FTPS и без LAN.

**6.2 FTPS + облачный MQTT.** Если LAN доступен: файл на SD как сейчас,
`project_file` с `url: ftp:///...` шлётся через облачный брокер. Полезно, когда
принтер не хочет качать с S3.

**6.3 G-code путь (самый совместимый без Dev Mode).** В Bambu Studio:
`Export G-code` вместо 3MF (одна галочка). PrintFlow принимает `.gcode` уже
сейчас (`handle_upload`, `estimate_file`). Заливка FTPS → команда
`print.gcode_file`. Работает на стоковых прошивках без подписи.

**6.4 Handy-handoff.** Файл уже в облаке → пользователь жмёт одну кнопку в
Bambu Handy; PrintFlow продолжает мониторинг/учёт/уведомления. Причина
возможного отказа (HMS 84033543) показывается честно, с пояснением, что это
ограничение стоковой прошивки для сторонних `project_file`, а не сбой PrintFlow.

**6.5 LAN + Developer Mode** остаётся целиком: для тех, кому локальность важнее
Handy. В этом режиме всё работает как в текущей версии.

## 7. Безопасность

- Токен Bambu — это ключ ко всему аккаунту: хранится только в `DATA_DIR`
  (`settings`, `SECRET_SETTINGS`), не попадает в Git, HTML, JS, бэкап браузера
  (механика уже есть и проверена для Telegram-токена).
- Данные печати идут через облако Bambu — это плата за отказ от LAN Only.
  Принтер и так в облаке (иначе способ не работает), нового раскрытия нет.
- Порт 6000 (камера) наружу не открываем; удалённый просмотр — Handy или VPN
  (как и написано в README).
- Кнопка «Выйти» стирает `cloud_token` и переподключает принтеры в LAN-режим,
  если он настроен.

## 8. Что сознательно НЕ делаем

- **Облачный видеопоток** (TUTK P2P, ttcode) — проприетарный, ломается чаще
  всего остального; камера остаётся LAN-6000 (работает без LAN Only).
- **Свой слайсер/подпись команд** (slicer_key.pem и т.п.) — против правил
  Bambu и хрупко; для подписи есть легальный Dev Mode, для всего остального —
  пути 6.1–6.4.
- **Открытие портов принтера в интернет** — только облако или VPN.

## 9. Риски и их снятие

| Риск | Вероятность | Снятие |
|---|---|---|
| Cloudflare блокирует login | Средняя | Слайсерные заголовки, ретраи, опц. `cloudscraper`/`curl_cffi`, ошибка с инструкцией |
| Bambu поменяет HTTP API | Средняя | Весь облачный код в одном `bambu_cloud.py`; фолбэки 6.2–6.4 не зависят от API; `doctor` покажет, что именно сломалось |
| Токен истёк (~3 мес) | Высокая | Бейдж «войдите заново», перелогин по email+коду одной кнопкой; MQTT при этом падает → событие в журнал |
| `project_file` отклонён (84033543) | Средняя | Пути 6.2/6.3/6.4, честный текст в UI |
| Два клиента MQTT от одного аккаунта конфликтуют | Низкая | Один CloudBridge на аккаунт (см. §3) |
| Принтер ушёл в LAN Only вручную | — | В облачном режиме показываем «принтер не виден в облаке — верните облачный режим или переключите PrintFlow на LAN» |

## 10. План внедрения

**Фаза 1 — облачный мост (1–2 дня):** `bambu_cloud.py` (login/uid/devices/tasks),
`cloud_bridge.py`, поле `mode`, подключение BambuPrinter к облаку, телеметрия и
команды через облако. Мониторинг, пауза/стоп/свет/скорость/AMS — работают
без LAN Only. Тесты: мок-логин, маршрутизация сообщений bridge, snapshot.

**Фаза 2 — облачная печать (1–2 дня):** `upload_project` (6 шагов),
`project_file` с cloud URL, фолбэки 6.2/6.3, `handle_upload` для облака,
прогресс заливки. Тесты: парсинг ответов upload, выбор фолбэка.

**Фаза 3 — UI и настройка (1 день):** секция «Bambu Cloud» в Настройках,
форма принтера с `mode`, облачный список в «Найти принтеры», бейджи, вкладка
облачных файлов, тексты ошибок, `doctor`.

**Фаза 4 — история и полировка (1 день):** `sync_cloud_history` (вес/время/фото
в журнал), обновление README/КАК-ЗАПУСТИТЬ.txt, регрессия существующих тестов
(LAN-режим не должен измениться).

Итого ~5–6 рабочих дней. Каждая фаза — работающая система: после Фазы 1
принтер уже не нужно переводить в LAN Only для мониторинга и управления.
