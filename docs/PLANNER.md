# Planner 1.0

Planner превращает общую цель человека в **preview-план**, но сам ничего не
исполняет. Реальное выполнение начинается только после отдельного решения
человека и всегда проходит через Task Engine.

## Поток

```text
цель человека
    ↓
Planner
    ↓
локальная модель предлагает skills
    ↓
сервер заново валидирует каждый skill + params + availability
    ↓
PREVIEW
    ↓
человек нажимает «Запустить план»
    ↓
Task Engine
    ↓
Agent.run_skill
    ↓
обычные confirmations / safety policy
```

Пример:

```text
Ноза, составь план как подготовить компьютер к работе
```

NOZZA может предложить:

1. открыть Telegram;
2. открыть PrintFlow;
3. открыть Bambu Studio.

Это ещё **не действия**. План появляется в разделе «Задачи». Только кнопка
«Запустить план» превращает preview в persistent Task Engine задачу.

## Почему preview отдельный

Планировщик использует LLM, а значит его вывод нельзя считать командой ОС.
Модель имеет право только предложить:

- точное имя зарегистрированного skill;
- параметры этого skill;
- краткое объяснение шага.

После ответа модели сервер независимо проверяет:

- skill существует;
- он доступен на этом компьютере;
- параметры соответствуют schema;
- planner не вызывает запрещённые meta-skills;
- шагов не больше 8.

## Двойное подтверждение

Одобрение preview означает только:

> «Да, этот план в целом можно выполнять».

Если внутри плана есть `write/system/irreversible` skill, Task Engine всё равно
остановится на нём и потребует обычное confirmation.

Поэтому:

```text
Approve plan != approve all dangerous actions
```

## Draft ID

UI не отправляет серверу отредактированный список шагов при approve. Preview
хранится внутри Planner и получает opaque ID. `approve(id)` использует именно
серверную копию и повторно валидирует её прямо перед созданием Task Engine
задачи.

Это защищает от подмены payload между preview и запуском.

## Время жизни

Preview живёт 10 минут. После этого его нужно построить заново. Одобренный plan
одноразовый и удаляется из draft cache после успешного создания задачи.

## Запрещённые meta-skills

Planner 1.0 намеренно не может сам планировать:

- `voice.command`;
- создание/запуск/удаление макросов;
- обучение/забывание;
- bootstrap;
- изменение watchdog config.

Такие изменения остаются явными командами владельца.

## API

Agent port, обычно `127.0.0.1:8799`:

```text
GET  /plans
POST /plans
```

Preview:

```json
{"op":"preview","goal":"подготовь компьютер к работе"}
```

Approve:

```json
{"op":"approve","id":"opaque-plan-id"}
```

Discard:

```json
{"op":"discard","id":"opaque-plan-id"}
```

## Voice / chat

Brain перехватывает только **явный** запрос на планирование:

- «составь план …»;
- «сделай план …»;
- «предложи план …»;
- «спланируй …»;
- «разбей на шаги …».

Обычная команда не отправляется в Planner автоматически.

## Native UI

Раздел «Задачи» содержит:

- поле цели;
- кнопку «Составить план»;
- preview-карточки;
- список шагов;
- risk каждого шага;
- пометку, если шаг потребует отдельного confirmation;
- «Запустить план»;
- «Отменить план».

## Граница Planner 1.0

Planner строит план только один раз. Он пока не занимается динамическим replan,
если внешний мир изменился во время исполнения. Это задача следующего слоя:
**Planner 2.0 / Observe → Verify → Replan**.
