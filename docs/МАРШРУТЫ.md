# Маршруты API PrintFlow — реестр и правило

Дата замера: 13.09.2026, версия 17.0.16.

Маршрутов в сервере **512**: 434 объявлены `if path == "/api/…"` внутри
`Api.get()`/`Api.post()` (и частично в `http_handler.py`), 78 — декоратором
`@router.get`/`@router.post` из `connector/printflow/router.py`.

Порядок разбора запроса: `Api.get()` и `Api.post()` **сначала** спрашивают
реестр декораторов (`api.py:988`, `api.py:2018`) и только если маршрута там
нет — идут по if-цепочке. Поэтому путь, объявленный и декоратором, и
if-цепочкой, во втором месте **мёртв**: до него никогда не доходит очередь.
Таким был `/api/search` (ветка в `api.py` против живого
`routes_system.search`) — снято в 17.0.16.

## Правило для нового маршрута

1. Новый маршрут объявляется **декоратором** в `routes_*.py`: у него есть
   `public`, `roles`, `audit`, `idempotent` и `doc`, и он сам попадает в
   `/api/openapi.json`. If-цепочка в `api.py` ничего из этого не даёт.
2. Путь не должен совпадать с уже объявленным для того же метода: реестр
   бросает `ValueError("Маршрут уже объявлен")` при загрузке, а контракт
   `connector/tests/test_routes_registry.py` ловит пару «декоратор +
   if-цепочка», которая не падает, а молча делает ветку мёртвой.
3. Каждый путь, который набирает фронт (`site/**/*.html`,
   `site/assets/*.js`), обязан существовать в сервере — это проверяет тот же
   тест. Так в 17.0.16 нашлась палитра команд, читавшая старый плоский ответ
   `/api/search`.
4. Перенос существующего маршрута из if-цепочки в декоратор — отдельный
   коммит: меняется способ разбора, а не поведение.

## Что этот реестр не делает

Справка не подменяет живой реестр и не претендует на полноту описаний:
единственный источник правды о маршруте — его объявление в коде. Числа здесь
нужны, чтобы рост API был виден, а `test_routes_registry` не даёт им
разойтись с кодом молча.
