## 3. Разбор: где контур заказов теряет время и деньги

### 3.1 Свои статусы ломают канбан (проверено живой пробой)

`repo.set_order_status` (`repo.py:412`) держит жёсткую таблицу переходов из 8
идентификаторов: `new, estimate, prepay, queue, printing, post, ready, done`.
Статусы при этом — данные в базе и редактируются в интерфейсе (`ops.js:2543`),
новый получает id вида `st_<время>` (`ops.js:3380`).

Проба на временной базе:

```
создан: 1001 new
new->estimate: estimate
estimate->st_delivery: ОТКАЗ -> Переход «estimate» → «st_delivery» запрещён
->stocked: ОТКАЗ -> Переход «estimate» → «stocked» запрещён
```

То есть редактор статусов работает, а перетащить карточку в свой статус нельзя
никогда. Для `stocked` это задумано (`config.py:451` прямо пишет «его нельзя
ставить перетаскиванием»), для произвольного статуса — нет. Лечится З15.

### 3.2 Перетаскивание не работает пальцем

`bindDrag` (`ops.js:355`) навешивает только `dragstart` / `dragover` / `drop` —
события HTML5 Drag and Drop. На сенсорном экране они не возникают. Касса
PrintFlow — это телефон и планшет (`android/`, `site/cashier.html`), то есть
основной сценарий вкладки недоступен на том устройстве, где им пользуются.
Лечится З14.

### 3.3 Пакетная смена статуса: частичное применение и нет аудита

`api.py:3359` — цикл по id, внутри `set_order_status`, без общей транзакции.
Каждый `save_order` — своя транзакция (`repo.py:194`). На первом запрещённом
переходе исключение уходит наружу: часть заказов уже изменена, часть нет,
клиенту приходит ошибка. Отдельно: одиночная смена пишет
`self._audit("order", …)` (`api.py:2336`), пакетная — только общее событие
«Пакетная смена статуса», без разбивки по заказам. Лечится З18/З19.

### 3.4 История заказа пишется и не показывается

`order_history` заполняется на каждое изменение поля (`repo.py:317`), маршрут
`/api/order/history` отвечает (`api.py:1339`) — и ни один файл в
`site/assets/` его не вызывает (проверено grep'ом). Готовая ценность лежит в
базе мертвым грузом: ни «когда обещали», ни «кто двигал», ни времени на этапах.
Лечится З83 и З31/З73.

### 3.5 Каждое действие тянет всю базу

`refreshCore` (`core.js:1355`) параллельно тянет `/api/orders`, `/api/customers`,
`/api/spools`, `/api/catalog`, `/api/jobs`, `/api/nomenclature` — без предела по
заказам. Замер на временной базе:

```
запись 1500 заказов: 1.2 с
repo.orders(): 0.152 с, строк 1500, JSON ~2 424 125 байт
```

И это вызывается после каждого перетаскивания (`ops.js:386`) вместе с
`PF.refreshFinance()`. Плюс `repo.orders` для каждой строки считает
`order_economics` (`repo.py:71`). На 1500 заказов одно движение карточки —
2,4 МБ по сети и пересчёт экономики по всей базе. Лечится З80/З81/З88.

### 3.6 Очередь не упорядочена по сроку

`repo.orders` сортирует `ORDER BY datetime(created_at) DESC` (`repo.py:58`),
канбан рисует список как пришёл (`ops.js:255`). Внутри колонки «Очередь»
сверху оказывается самый старый созданный заказ, а не самый горящий. Поле `due`
при этом есть, живёт на карточке и даже тикает (`liveDueText`, `ops.js:23`).
Лечится З12.

Дополнительно: `due` — только дата (`db.py:692`), время выразить нельзя, а
`liveDueText` считает остаток до 23:59:59. «Сдать к 18:00» система не понимает.

### 3.7 Удаление вместо архива

`delete_order` (`repo.py:438`) отвязывает `print_jobs`, `payments`,
`transactions`, удаляет `order_items` и сам заказ. `order_history`,
`order_photos`, `defects`, `documents` не трогаются. Проба:

```
order_history: сирот 1
order_photos: сирот 1
defects: сирот 1
documents: сирот 1
архивных колонок у orders: нет
```

Заказ исчезает безвозвратно, а его следы повисают ни на чём. Лечится З53.

### 3.8 Главная операция вкладки не покрыта тестами

`grep -rn "set_order_status\|bulk-status" connector/tests/` не находит ничего.
Из 2427 строк `test_order_*` ни одна не проверяет переходы статусов — то, чем
вкладка пользуется постоянно. Лечится З85.

### 3.9 «Готов» — тупик

`allowed["ready"] = {"post"}` (`repo.py:429`), `allowed["done"] = set()`.
Перепечатку бракованного готового заказа нельзя начать одним движением: только
назад в «Постобработку» и дальше по цепочке. Лечится З17.

## 4. Варианты перестройки

Цена в рублях = часы × ставка владельца. Ставку я не знаю и выдумывать не буду
(см. §6, вопрос 1) — поэтому здесь только часы.

### Вариант A. Точечные правки, модель не меняется

З12, З16, З18, З81, З83, З84, З85, З86, З3, З7, З17, З48, З74.

- **Цена:** 14–20 ч.
- **Что ломает:** порядок карточек в колонках (З12) — заметит владелец в первый
  же день; `bulk-status` начнёт отвечать списком отказов вместо ошибки —
  правка теста, если он появится.
- **Миграция данных:** не нужна, кроме `CREATE INDEX IF NOT EXISTS` на `due`.
- **Откат:** `git revert` по каждому коммиту; индекс можно оставить.
- **Что не решает:** свои статусы по-прежнему нельзя перетащить, канбан
  по-прежнему не работает пальцем, 2,4 МБ на рефреш остаются.

### Вариант B. Порядок в статусах + рабочее перетаскивание

Вариант A целиком + З15 (переходы как данные), З14 (touch-drag), З19, З80
(пагинация), З53 (архив), З20–З23.

- **Цена:** 40–60 ч.
- **Что ломает:** `set_order_status` меняет источник правил — все 10 файлов
  `test_order_*` должны остаться зелёными, для штатных 8 статусов поведение
  обязано быть побитово прежним (это отдельный тест). `orders` получает
  колонку `archived` — через `ADDED_COLUMNS`, идемпотентно, без удаления и
  переименования.
- **Миграция:** `ALTER TABLE orders ADD COLUMN archived INTEGER DEFAULT 0`;
  `ALTER TABLE statuses ADD COLUMN next_ids TEXT DEFAULT ''`; для существующих
  8 статусов `next_ids` заполняется текущей таблицей `allowed` один раз при
  старте, если колонка пуста. Живые базы владельца переносятся автоматически,
  без ручных действий.
- **Откат:** колонки остаются (удалять нельзя по правилу репозитория), код
  возвращается `git revert`; при пустом `next_ids` сервер обязан работать по
  прежней жёсткой таблице — это и есть механизм отката.
- **Что не решает:** карточка заказа остаётся одной длинной формой.

### Вариант C. Вкладка «Заказы» заново

Вариант B + З93 (карточка с вкладками), З82 (виртуальный рендер), З91/З92
(вынос чужих разделов из `ops.js`), З31/З73 (время по этапам), З25 (preflight).

- **Цена:** 110–160 ч.
- **Что ломает:** разметка модалки `dialog#order_modal` (`index.html:3974`) и
  контракты вёрстки `connector/tests/test_site_markup.py` — их придётся
  обновлять осознанно и описывать в отчёте. `ops.js` делится на модули:
  меняется подключение и `?v=` в разметке, поднимается `CACHE` в `sw.js`.
- **Миграция данных:** не нужна — модель та же.
- **Откат:** тяжёлый. Нужна ветка и сохранение старого `ops.js` рядом до
  приёмки; кэш-версия откатывается одним числом.
- **Риск:** самый высокий по привычке — владелец работает в этой вкладке каждый
  день.

### Вариант D. Новая модель данных (не рекомендую)

Разделить `orders` на заказ клиента, производственное задание и факт выдачи.

- **Цена:** 300+ ч, из них не менее трети — перенос данных.
- **Что ломает:** всё, что читает `orders` — а это касса, долги, клиентский бот,
  витрина, отчёты, 10 файлов `test_order_*`. Денежный контур задевается
  неизбежно, а это запрещено правилами раунда.
- **Откат:** фактически невозможен без восстановления из копии базы.
- **Заключение:** текущая модель покрывает цех с одним принтером. Проблемы
  вкладки — в порядке данных, в переходах статусов и в объёме выборки, а не в
  схеме. Решаются вариантом B.
